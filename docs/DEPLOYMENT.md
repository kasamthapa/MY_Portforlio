## Build contract

```sh
npm ci
npm run build
```

`build` runs `tsc && vite build`. Vite copies `public/` to the output and emits bundled assets under `dist/assets/`. This app does not require runtime API keys or environment variables. `dist/` is ignored and is generated by the host; commit source assets and lockfiles, not the built directory.

GitHub activity uses a public browser feed and a dated JSON snapshot bundled into the app. Refresh that fallback with `node scripts/update-github-activity.mjs` when appropriate, review the resulting source data, then rebuild. This is an explicit maintenance step, not a build-time network requirement. A feed outage preserves saved data and does not require hosting secrets; see [GitHub activity](GITHUB_ACTIVITY.md).

Use `npm run preview` for a local production preview when needed. No test/lint scripts are configured; a successful build is not an automated browser test.

## Release through the existing Git connection

Only publish when the user authorizes it. Once authorized:

1. Review the working tree, staged files, and any previously unpushed commits. Include the scope the user requested, preserving unrelated work.
2. Run the appropriate build and inspect the result. Review staged content for accidental secrets, temporary files, or missing assets.
3. Refresh the remote branch before pushing. If it advanced, reconcile the history without discarding either side; do not force-push.
4. Commit with a message describing the release, then push `main` to `origin/main`.
5. Record the exact resulting commit SHA. Check its **Vercel** GitHub status until it succeeds or fails.
6. After success, confirm the public domain serves the new bundle/assets and the expected page behavior. A successful push alone does not prove deployment.

Useful local commands:

```sh
git status --short --branch
git fetch origin
git log --oneline origin/main..HEAD
git diff --cached --stat
git diff --cached --check
git push origin main
```

A GitHub connector's commit-status tool or GitHub's repository status/deployment APIs can verify the exact release. Use the deployment's returned URL rather than guessing hostnames. Never print authentication tokens into logs or commit them to a file.

## Direct CLI deployment

The Vercel CLI may be installed on a developer's machine, but that does not mean it is authenticated or linked to this project. The documented release environment did not have a usable CLI login. Prefer the existing Git integration. If a direct deployment is genuinely required, first confirm authentication and the existing project/production target; do not run an automatic project-creation flow.

Machine-specific `.vercel/` metadata, local CLI credentials, and environment files must stay out of Git.

## Failures and rollback

- **Build fails:** fix the source/build error before publishing. Do not mark an earlier successful deployment as the current release.
- **Push fails:** report the exact local commit and whether any remote update occurred. Do not retry with force.
- **Deployment fails:** inspect the Vercel build status/logs for that commit, fix the cause, and push a new commit through the same integration.
- **Domain still serves old assets:** check deployment readiness and domain assignment; distinguish propagation/caching from a failed build.
- **Rollback:** prefer reverting the problematic Git commit and letting the existing integration deploy the revert. A host rollback should target a verified successful deployment and requires the user's authorization.

Keep the canonical URL synchronized across HTML metadata, sitemap, robots, and any host-level domain configuration if the owner changes domains.
